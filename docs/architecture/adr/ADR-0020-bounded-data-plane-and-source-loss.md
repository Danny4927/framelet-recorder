# ADR-0020: Core-owned bounded data plane, overload policy, and source loss

- **Date:** 27 November 2026
- **Status:** Proposed — implemented for review; a human maintainer must accept it before roadmap criterion A-7 can be ticked
- **Amends (on acceptance):** ADR-0012 decision 3 (media pipeline accepts payloads through its port); ADR-0017 decision 5 (call order) as listed below. The accepted text of both ADRs is not edited.
- **Related:** ADR-0005, ADR-0009, ADR-0012, ADR-0017, ADR-0018, ADR-0021; roadmap Phase A deliverable A3

## Context

ADR-0017 gave the application service a typed control plane but left the data plane open: `MediaPipelinePort` had `push_video`/`push_audio`, which only the application service could call because it alone holds the port. Routing every frame and audio block through the service worker would couple media throughput to command handling, and letting a capture adapter call the media adapter directly would be adapter-to-adapter coupling (forbidden by AGENTS.md). The overload rules — "video drops are counted", "audio loss is never silent" (SPECIFICATION.md §5.4, REQ-FLOW-01..03) — existed only as prose, so every future adapter would have had to re-implement them, and nothing tested that queues stay bounded. Finally, `RecordingEvent::SourceLost` existed but nothing could raise it, and the specification requires a mode-dependent reaction to camera and microphone loss (§9, REQ-ERR-05/06).

## Decision

1. **Core-owned sinks and streams.** `framelet-core::data_plane` provides bounded single-producer/single-consumer channels: `VideoSink`/`VideoStream` for owned `VideoFrame`s and `AudioSink`/`AudioStream` for owned `AudioBlock`s (delivered as `AudioPacket`). Capacity is fixed at construction and validated (`1..=MAX_VIDEO_QUEUE_CAPACITY` = 64 frames, `1..=MAX_AUDIO_QUEUE_CAPACITY` = 1024 blocks; these are ceilings, not sizing advice). Queue length can never exceed the capacity. Implementation: `Mutex<VecDeque>` + `Condvar` from `std`; no new dependency, no `unsafe`.
2. **Who creates and who holds them.** `MediaPipelinePort::prepare(recording_id, &RecordingConfiguration, &OutputTarget)` builds the channels with `data_plane::media_inputs(configuration, StreamCapacities)`, keeps the receiving `MediaStreams`, and returns `PreparedMedia { session, sinks: MediaSinks }`. `MediaSinks` can only be created by `media_inputs`, so it always holds one sink per source of *some* configuration; the application rejects sinks that do not match the session's configuration (`MediaSinks::matches`) and rolls back (`media.abort`, `storage.abort`). At `start` the application moves each sink into the capture port: `ScreenCapturePort::start(&source, VideoSink)`, `CameraCapturePort::start(&source, VideoSink)`, `MicrophoneCapturePort::start(&source, AudioSink)`. Capture and media adapters never see each other. `prepare` receives the whole configuration rather than only the mode, because the optional microphone changes which sinks exist.
3. **Non-blocking delivery with a per-stream overload policy.** `try_send` never blocks on a full queue and returns a `#[must_use]` outcome:
   - video: `VideoDelivery::Accepted`, `DroppedStale { dropped_total }` (the *oldest* queued frame is discarded so the newest is kept — stale frames are the ones to drop, SPECIFICATION.md §5.4), or `Closed` (consumer gone);
   - audio: `AudioDelivery::Accepted`, `Discontinuity { lost_blocks_total }` (the *newest* block is rejected, every accepted block is kept, the loss is counted, and the next accepted block carries `gap_before: Some(AudioGap { lost_blocks, lost_frames })`), or `Closed`.
   `StreamStats` (capacity, queued, high-water mark, accepted, delivered, dropped, lost audio frames, discontinuity episodes, pending gap, end, consumer closed) is a consistent snapshot readable from either end and from a `StreamMonitor`.
   **Trailing loss:** audio rejected after the last accepted block is carried by no packet. It stays in `StreamStats::pending_gap`; after an audio stream has ended, the media pipeline must read its final `stats()` and account for a non-empty `pending_gap` exactly like a marked gap. This is part of the media pipeline contract and is covered by the suite `media::audio_trailing_loss_is_reported_after_stream_end`.
4. **Thread placement.** Sinks are for capture *workers*. `try_send` takes a short internal lock, so it must not be called from a real-time audio device callback; the callback keeps writing to a preallocated SPSC ring that a worker drains into the sink (ADR-0009 unchanged). The media pipeline consumes on its own worker. Before `start`, a pipeline does not consume from its streams, so sinks fill to capacity and then apply the policy; the contract suites rely on this to test overload deterministically for any adapter.
5. **Stream end and source loss.** Dropping a sink ends its stream with `StreamEnd::Stopped`; the consumer sees `Received::Ended(Stopped)` once the queue is empty. A capture adapter that loses its device calls `sink.report_source_lost()`, which consumes the sink (nothing can be sent after the loss) and ends the stream with `StreamEnd::SourceLost`. Capture `stop` stops the producer and releases the sink before returning, and is idempotent; a failed `start` releases the sink too. Dropping a stream (media `abort`/`close`) makes later sends return `Closed` and frees queued payloads.
6. **Source-loss outcome is a domain rule.** `RecordingConfiguration::source_loss_outcome(kind)` returns `StopRecording` for a source the mode itself records (screen; camera; microphone in microphone-only mode) and `ContinueWithout` for the optional microphone. The aggregate records the loss (`RecordingSession::record_source_loss`, `lost_sources()`) while Recording, Paused, or Finalizing, so a completed session with lost sources is visibly degraded.
7. **Source-loss path in the application.** The application keeps a `StreamMonitor` for every sink it hands out. A new inbound use case `RecordingUseCases::process_source_losses(recording_id)` — called periodically by the inbound adapter's recording worker (Phase C fixes the cadence; target ≤ 100 ms) — finds lost sources, stops their capture, publishes `RecordingEvent::SourceLost { recording_id, kind, source }` and then applies the outcome: continue (returns the state; a failed stop of the lost source is `CleanupIncomplete`), or stop the remaining sources, drain and close the pipeline so the kept candidate is as recoverable as possible, publish nothing, fail the session with `ApplicationError::SourceLost { kind, additional_failures }`. `stop` checks the monitors again after all producers have stopped, so a loss that happens just before Stop still prevents publication. A monitor is a flag, not a queue: loss signals cannot overflow or be lost. Every lost source found in one check is processed; a loss the aggregate rejects (an invariant violation) does not hide the others and stays tracked for the next check, and the rejection is returned as a typed domain error.
8. **Call order changes (amends ADR-0017 decision 5 on acceptance).** prepare: `storage.begin` → `media.prepare(…, &target)` → sink check → Ready. start: `media.start` → captures with their sinks (rollback: stop started sources, `media.abort`, `storage.abort`). stop: stop all captures → record losses → `media.drain` → `media.close` → `storage.publish(session, ClosedOutput)` (ADR-0021). cancel: `media.abort` → `storage.abort`. `stop` on an ended session (Completed, Failed, Cancelled) returns that state and touches no port (REQ-LIFE-11).

## Alternatives

- **Route payloads through the application service** (`push_video` on the port): rejected; couples media throughput to the control worker and forces every payload through `&mut` access to all ports.
- **Media adapter implements a sink trait itself:** rejected; every adapter would re-implement and could get wrong the overload policy and the bound. One core-owned implementation is tested once and inherited by all.
- **`std::sync::mpsc::sync_channel`:** rejected; it cannot drop the oldest frame, exposes no occupancy or high-water mark, and cannot attach a gap marker to the next accepted block.
- **Drop-newest for video** (as in the GStreamer PoC): rejected for the production contract; it keeps stale frames and increases latency under overload. The PoC remains a diagnostic.
- **Drop-oldest for audio:** rejected; it silently discards audio that was already accepted (ADR-0009).
- **Push-based source-loss notification** (a callback port implemented by the composition root, or a channel the service drains): rejected for now; it needs an extra port or a second receive path on the worker. A monitor flag plus a polled use case is lossless and needs no new port. Revisit if Phase C measurements show polling latency matters.
- **Stop on every source loss:** considered — simplest and never produces a degraded artifact. Rejected because SPECIFICATION.md §9 allows continuing when the active mode stays valid. *Review point for acceptance:* continuing without the optional microphone completes a recording whose later part has no audio; the loss is published as an event and recorded on the aggregate, but the `Completed` event does not yet carry it (see Consequences).

## Consequences

- No capture adapter can deliver a payload except through a bounded, core-owned sink; queue bounds and overload accounting are a property of the core, verified once.
- `MediaPipelinePort` loses `push_video`/`push_audio` and gains `abort`; `close` now returns `ClosedOutput`. Capture `start` takes a sink. Every adapter written after this ADR uses these signatures.
- `try_send` takes a lock; it is fine for capture workers but not callbacks. A lock-free design would require reviewed third-party code or `unsafe` and is not justified without measurements.
- Memory is bounded per stream by capacity × frame size; `VideoFrame` itself has no configured maximum dimension yet (REQ-CAP-05, Phases C/E).
- Overload is counted and marked but not yet surfaced to the user: wiring `StreamStats` into `RecordingMetricsPort`, a degraded flag on `Completed`, and the UI message are Phase C work (C-3, REQ-FLOW-02/03, REQ-ERR-06).
- Format changes inside a stream (sample rate, channels, pixel format) are not checked by the sink; the media adapter validates them (ADR-0009 queue rules still apply).

## Validation

- `crates/core/src/data_plane_tests.rs`: capacity validation; video drop-oldest with exact drop counts and order; audio reject-newest with one gap per overload episode and the gap marker on the next accepted block; end of stream on drop and on source loss; closed consumer; blocking receive wakes on item and end; a concurrent producer of 2 000 frames never exceeds capacity and `delivered + dropped == accepted`.
- `data_plane_tests.rs`: `trailing_audio_loss_is_reported_in_final_stats_after_stream_end`, `marked_gap_is_no_longer_pending`.
- Shared contract suites in `crates/core/src/contract/` (`media::video_overload_counts_drops`, `media::audio_overload_yields_discontinuity`, `media::audio_trailing_loss_is_reported_after_stream_end`, `media::queues_never_exceed_capacity`, `media::prepares_sinks_for_exactly_the_required_sources`, `capture::*`), passed by the fakes (`framelet_core::contract::tests`). Every future media and capture adapter must pass them (Slice Definition of Done).
- Application tests: `captured_media_flows_through_core_owned_sinks_to_the_pipeline`, `trailing_audio_loss_reaches_the_pipeline_through_final_stats`, `rejected_loss_does_not_hide_other_losses_and_stays_tracked`, `essential_source_loss_stops_without_publishing_and_keeps_candidate`, `optional_microphone_loss_continues_and_is_recorded_on_the_session`, `source_loss_seen_only_at_stop_still_prevents_publication`, `media_sinks_that_do_not_match_the_configuration_are_rejected_and_rolled_back`, `stop_is_idempotent_and_touches_no_port_after_the_session_ended`; domain tests `source_loss_outcome_depends_on_mode`, `aggregate_records_source_loss_only_while_capturing_and_for_used_sources`.
- Not yet validated: real-device loss (C-5, F-4), sustained overload with a real encoder (D-4), polling latency.
